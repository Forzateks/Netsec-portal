# On-Prem Backup of Supabase — Design

**Date:** 2026-08-18
**Status:** Design approved. Open items 1 and 4 resolved and verified against the live
database 2026-08-18. Pending implementation plan.
**Audience:** Mohammed Nasif (primary), Venkatesan. Written for someone who has
not administered a Linux server before.

---

## 1. What problem this solves

**The risk.** Supabase holds the only live copy of every session, leave request,
OT record, contract and inventory item. If the project is deleted, the account is
compromised, or billing lapses, Supabase's own backups die with it — they live
inside the same account.

**Today's protection.** The in-app **Full Backup (Excel + SQL .zip)** plus
`docs/disaster-recovery.md`. It works, but it is *manual*. The real exposure is
"everything since somebody last remembered to click the button."

**This design.** An automated nightly copy onto hardware Gulfit owns, verified by
actually restoring it, with a failure signal that surfaces inside the app.

### What this deliberately does NOT do

Scoped down from the original idea (realtime replication with automatic failover)
after establishing that the failure being defended against is **permanent data
loss**, not downtime. Explicitly out of scope:

- **No failover.** If Supabase is down, the app is down. Nobody works offline.
- **No realtime replication.** Up to 24h of work can be lost. Accepted.
- **No auth replication.** Logins are not mirrored.
- **Nothing internet-facing.** The VM opens no inbound ports.

Those were dropped because the app is a **static browser-only SPA** — every
browser talks to Supabase directly, with no backend in between. Failover would
mean each browser switching URLs, which additionally requires mirroring GoTrue
auth and JWT signing, and creates split-brain on write (primary keys are
`bigint GENERATED BY DEFAULT AS IDENTITY` and would collide across two live
databases). That is a large, fragile system to defend against a few hours of
downtime the business can absorb.

## 2. Architecture

One-way. The on-prem server **pulls**; Supabase never initiates anything.

```
Supabase Cloud (source of truth)
      |   nightly 02:00, outbound only
      v
Ubuntu VM (VMware, on-prem)
   |-- /var/backups/netsec/netsec-YYYY-MM-DD.sql.gz    30 daily + 12 monthly
   \-- local PostgreSQL  <- restored fresh every night (this is the test)
            |
            \--> INSERT one row into Supabase backup_log
                        |
                        \--> the app's existing dashboard staleness
                             banner goes stale if this stops
```

The app is **not modified**. It does not know this exists.

## 3. The VM

| Resource | Value | Why |
|---|---|---|
| OS | **Ubuntu Server 24.04 LTS** | Free; official PostgreSQL packages; security updates to 2029; the OS almost every Postgres guide assumes |
| vCPU | 2 | Dump and restore are not CPU-bound at this size |
| RAM | 4 GB | Comfortable for a small Postgres |
| Disk | 60 GB | The database is well under 1 GB; compressed dumps are tiny. Holds years |
| Network | Outbound internet only | **No inbound ports. No port forwarding. No DMZ.** |
| Desktop | None | Managed over SSH |

Software: `postgresql-17`, `postgresql-client-17`, `gzip`, `cron` (already present).

> **`pg_dump` version rule.** The client version must be **greater than or equal
> to** the Supabase server's PostgreSQL version, or it refuses to run. Check the
> server version first (Supabase dashboard, Settings, Infrastructure) and install
> a client at least that new. This is the most common reason a first attempt
> fails.

## 4. Connecting to Supabase

Supabase has retired direct IPv4 connections, so this uses the **Session Pooler**
string from Settings, Database, Connection string, *Session pooler*:

```
postgresql://postgres.<project-ref>:<password>@aws-0-<region>.pooler.supabase.com:5432/postgres
```

Use the **session** pooler, not the transaction pooler on port 6543 — the
transaction pooler does not support `pg_dump` correctly.

The password is the **database password**, which is *not* the anon key in
`js/core/state.js`. It lives in `~/.pgpass` with `chmod 600`, never inline in the
script and never committed to git.

## 5. What runs each night

A single script, `/opt/netsec-backup/backup-netsec.sh`, run by cron at 02:00.

**Step 1 — Dump.**
`pg_dump --schema=public --no-owner --no-privileges` into
`netsec-YYYY-MM-DD.sql.gz`.

`--schema=public` because that is what restores cleanly into a fresh Supabase
project. `--no-owner --no-privileges` because Supabase's internal roles do not
exist on the local Postgres and would otherwise produce restore errors.

A second, tiny export lists `auth.users` (id and email only) so that during a real
recovery you know exactly who to re-invite. Passwords are *not* exported — the
existing runbook already has the manager re-invite users, who then set their own.

**Step 2 — Check the dump before trusting it.**
A `pg_dump` that fails midway still leaves a file. Before it is treated as good:

- file size is above a floor, and not wildly below yesterday's
- the file ends with PostgreSQL's completion marker
- the set of `CREATE TABLE` statements is **not smaller than last night's**

The table check compares against the previous dump rather than a hardcoded list.
That is deliberate: a fixed list is exactly the thing that silently drifted in the
app's own backup (see section 9), and a self-comparing check needs no maintenance
when a table is added.

If any check fails: keep yesterday's dump, do not rotate, write nothing to
`backup_log`, exit non-zero.

**Step 3 — Restore into local Postgres.**
Drop and recreate the local `netsec_backup` database, restore the fresh dump.
*This is the verification.* A dump that cannot be restored is not a backup, and
the only way to know is to restore it.

**Step 4 — Row-count comparison.**
Count rows per table, compare against the previous night (stored in a small local
table). Log every table and flag any that moved more than a threshold — suggested:
a drop of more than 20% or more than 100 rows. This catches two different
disasters: a subtly broken dump, and **accidental mass deletion in production**,
the second being what a backup is most likely to be needed for.

**Step 5 — Rotate, then report.**
Keep 30 daily and 12 monthly dumps; delete the rest. Then insert into Supabase
`backup_log`:

| Column | Value |
|---|---|
| `taken_by` | `Automated (on-prem)` |
| `taken_by_email` | a service identity, e.g. `backup@gulfitd.com` |
| `file_size_bytes` | size of the dump |
| `table_count` / `row_count` | from step 4 |
| `notes` | `verified restore OK`, plus any row-count flags |

`taken_by` is deliberately distinguishable from a human clicking Full Backup.

## 6. How you find out it broke

The part that matters most, because backup systems characteristically fail
silently for months and are discovered only during the disaster.

Step 5 writes to `backup_log`, which **already** drives the dashboard's backup
staleness banner. If the nightly job dies for any reason — VM off, disk full,
password rotated, Supabase unreachable — no row is written, the banner goes
stale, and a manager sees it on the dashboard the next morning.

No new alerting system is built or maintained, and the design **fails loudly by
default**. The script also writes `/var/log/netsec-backup.log` for diagnosis.

---

## 7. Security

The dump is the entire company database in one file, and **RLS provides no
protection at rest** — `pg_dump` runs with full read access by design.

- `/var/backups/netsec/` owned by a dedicated `netsecbackup` user, mode `0700`
- `~/.pgpass` mode `0600`
- VM disk encrypted at the VMware layer, or LUKS inside the guest
- No inbound ports; SSH only from the internal network
- Database password rotated if anyone with access leaves
- Dumps must **never** be copied into the git repo

Note for a network-security consultancy: this adds no attack surface. It is an
outbound-only pull to a host that accepts no inbound connections.

---

## 8. Restore drill

A backup nobody has restored is a hope. **Twice a year**, run a real drill:

1. Create a throwaway Supabase project.
2. Restore the newest dump into it.
3. Point a local copy of the app at it by changing `SUPABASE_URL` and
   `SUPABASE_KEY` in `js/core/state.js` — *locally only, never committed*.
4. Log in. Open Dashboard, My Sessions, Leave Overview. Confirm the data is there.
5. Delete the throwaway project. Record the date in `docs/disaster-recovery.md`.

Step 3 is what proves the dump is not merely valid SQL but actually *runs the
application*.

## 9. Known limitations

- **Up to 24h of data loss.** Accepted trade-off. Revisit by running the same
  script more often (a different cron line) if that stops being acceptable.
- **One copy, not three.** One on-prem server is a single fire, flood or
  ransomware event away from gone. A future improvement is one offsite copy, for
  example encrypted to object storage. This design is strictly better than today,
  not complete.
- **Ransomware reaches mounted backups.** If the VM is compromised, the dumps on
  it are compromised too. Offsite or write-once storage is the answer.
- **Auth users are listed, not restored.** Recovery re-invites them, exactly as
  the current runbook already describes.
- **Advantage over the in-app backup:** the app's Full Backup uses a
  hand-maintained list of tables in `dashboard.js`. It has drifted before — v143
  records that `tasks` and `team_members` were missing from every backup until
  someone noticed — and it is drifted **right now**: `docs/schema.sql` defines 31
  public tables while `BACKUP_TABLES` covers 30 (`backup_log` itself is absent).
  That gap is harmless today, but it is the same failure mode recurring. A
  `pg_dump` has no list to drift.

## 10. Open items to resolve during implementation

1. ~~Supabase server PostgreSQL version.~~ **RESOLVED — PostgreSQL 17.6.**
   Verified live: `select version()` returns `PostgreSQL 17.6 on aarch64-unknown-linux-gnu`.
   So `postgresql-client-17` (or newer) is required, as specified in section 3.
2. The service identity email for `backup_log.taken_by_email`.
3. Whether disk encryption is done at the VMware layer or with LUKS in the guest.
4. ~~Whether RLS permits the `backup_log` insert for the key the script uses.~~
   **RESOLVED — no key is needed at all.**

   The anon key definitively cannot insert: both policies are `TO authenticated`,
   and `backup_log_insert_backup_responsible` further requires the JWT email to
   match a `user_profiles` row with `is_backup_responsible = true`. An anon key is
   neither authenticated nor carries an email claim, so it would fail with `42501`.

   But the script does not need a key. It already holds a direct Postgres
   connection for `pg_dump`, as the `postgres` role — and the table owner bypasses
   RLS unless `FORCE ROW LEVEL SECURITY` is set, which it is not anywhere in this
   schema. So step 5 is simply another `psql` statement down the same connection:

   ```bash
   psql "$CONN" -c "INSERT INTO backup_log (taken_by, taken_by_email,      file_size_bytes, table_count, row_count, notes) VALUES (...)"
   ```

   This removes a whole credential from the design — no anon key, no service-role
   key, no new policy, nothing extra to store or rotate on the VM.

   **Verified live 2026-08-18:** `rls_forced = false` on `backup_log`, and zero
   tables in the `public` schema set `FORCE ROW LEVEL SECURITY`. The connection
   reports `current_user = postgres`. The approach is confirmed against the real
   database. To re-check later (read-only):

   ```sql
   select relrowsecurity as rls_enabled, relforcerowsecurity as rls_forced
   from pg_class where oid = 'public.backup_log'::regclass;
   ```

   **Verify on the VM** with a rolled-back transaction, which proves the permission
   without writing a row or disturbing the dashboard banner:

   ```bash
   psql "$CONN" -c "begin; insert into backup_log (taken_by, taken_by_email, notes)      values ('Automated (on-prem)','backup@gulfitd.com','permission test'); rollback;"
   ```
